# ADR 0049: run 动作由纯函数判定，取消只有一个翻译点

- 状态：已接受。细化 ADR 0037 的续跑点推导、ADR 0039 的接入边界与 ADR 0014 的取消语义
- 日期：2026-10-30

## 背景

`engine/mod.rs` 的执行循环同时承担三件事：判定下一步、执行副作用、以及四条没有单测的顺序约束——步数上限先于插话接入、工具执行期间不接插话、压缩失败只重试一次、收尾判定先于请求。四条规则只写在注释里，改动它们只能靠端到端测试发现回归。续跑点本身已经是纯函数（`recover::resume_point`，带 9 条单测），但它的调用顺序仍是隐含知识。

取消有五种落点：工具循环返回一个布尔、正在执行的工具写「工具失败：已取消」、未执行的调用写「结果未知」、模型流返回 `StepEnd::Cancelled`、run 结局是 `cancelled()`。压缩路径更远：压缩期间取消被记成 `context_limit_exceeded` 失败，界面因此把用户取消显示成上下文超限。

## 决策

**下一步判定收进 `engine/plan.rs` 的纯函数。** `next_action(transcript, run, max_steps)` 返回 `Plan { steer, action }`，`action` 取请求、工具、收尾、步数超限四值。限额只挡请求，未完成的工具批照常执行；限额用尽时插话留到下一次 run。

**步数按当前 transcript 里定型的 assistant 节点数。** 旧实现用一个只在首轮计算的计数器，计的是「已发出的请求数」，压缩与失败请求都记在里面。新口径只数链上看得见的定型消息，调用者不再计。

**压缩后的步数从零起算。** `MessageTree::transcript` 遇压缩节点即停，所以压缩之前的 assistant 节点不在 transcript 里，计数因此归零。这是有意接受的代价：压缩每 run 只发生一次，而压缩后的重试不占步数；代价是 `max_steps` 不再是请求次数的硬上限，最多可达 `2 × max_steps - 1`。若把已用步数改成显式输入可以保住旧口径，但那要求调用者维护计数，plan 就不再只是 transcript 的函数。

**接入插话是伴随字段，不是动作。** plan 读不到队列，若把「接入插话」当成动作，没有待插入插话时它会再次返回同一动作，驱动循环自旋。`steer` 表示「此刻允许接入」，执行循环据此调用 `Store::apply_pending_steers`，插入非空则重新判定。

**压缩不属于计划。** 压缩是对模型请求返回 `context_limit_exceeded` 的反应，无法从 transcript 推出。若让 plan 产出它，plan 必须把上一步的失败作为输入，等于把驱动循环的状态机搬进纯函数。压缩留在失败分支，「只压一次」由 `CompactionBudget::take` 表达，机会在尝试之前取用。

**取消只有一个翻译点。** 工具循环返回 `ToolLoopEnd::Completed | Cancelled`，模型流返回 `StepEnd::Cancelled`，压缩返回 `CompactionEnd::Compacted | Cancelled | Failed`；三者都由执行循环翻成 `RunOutcome`。判定位置不扩大：模型流已经正常结束、取消信号随后到达时，run 仍然成功。

**压缩期间取消以 `cancelled` 结束。** 不写压缩消息，`failure` 为空，界面不再把它显示成上下文超限。

**替换而非分层。** `recover::resume_point` 被 `plan` 吸收，`recover.rs` 删除，其用例迁入 `plan.rs` 并补齐顺序约束的用例。

## 备选

- **`Compact` 作为动作值**：plan 完整拥有全部决策，但输入要多一个「上一步的失败」，plan 变成跨轮状态机，测试反而要造两轮输入。
- **把已用步数作为 plan 的显式输入**：保住旧口径与 `max_steps` 的硬上限，但调用者要维护一个必须与 transcript 对齐的计数器，plan 不再是 transcript 的函数。压缩后归零的代价被接受，因此不取。
- **执行循环收尾处统一看取消信号**：判定点只有一处，实现最短，但会把「已完成却恰逢取消」记成取消，改变一处竞态语义。
- **把取消当错误值沿 `?` 传播**：代码最短，但取消与存储失败进同一通道，调用者容易把它当失败处理。
- **把插话数量作为 plan 的输入**：plan 仍是纯函数，但驱动要先读队列，队列长度于是有两个来源。
- **保留 `recover.rs` 作为 plan 的内部实现**：改动更小，但「下一步做什么」仍有两个 owner，读代码要继续跳一层。

## 后果

- 顺序约束进了纯函数的单测：步数上限先于请求、工具批不接入插话、收尾判定；接入动作本身仍由 `steer.rs` 的端到端用例覆盖。
- 步数上限不再等于请求次数上限：压缩后计数归零，最坏情况下一个 run 可发出 `2 × max_steps - 1` 次请求。规格只要求「超限以显式错误结束 run」，因此这不违背规格，但防失控闸门比旧实现弱。
- ADR 0037、ADR 0039 与 ADR 0014 的决策不变，只是实现位置变了：续跑点、接入边界与失败类别仍按原样生效。
- 压缩期间取消的 run 结局由 `failed` 加 `context_limit_exceeded` 变为 `cancelled`，客户端显示「已取消」。
- 不新增跨进程 seam：`plan` 的测试是模块内单测，不属于 ADR 0007 的 seam 清单。
- `recover.rs` 删除；`AGENTS.md` 的引擎导航与 `docs/glossary.md` 的「run 动作」条目随之更新。
