# ADR 0030: 上游 resync 只触发重连，不写节点状态

- 状态：已接受。细化 ADR 0018 的 resync 语义与 ADR 0021 的节点状态机
- 日期：2026-10-21

## 背景

`NodeWatcher` 把上游 `StreamEvent::Resync` 当成一次失败：写 `unreachable`，说明为「上游要求 resync」。触发条件是 `hub` 落后于 `agent` 的内存广播容量，此时节点是健康的：health 通过，SQLite 可读，命令能转发。

三处代价：

1. 该节点的全部命令被禁用，直到下一次连接成功（约 1 秒）。
2. 侧栏把「`hub` 落后」和「隧道断了」混成同一条说明，用户无法判断该做什么。
3. 每次落后都警告一次，持续落后时日志噪声与重连次数都放大。

`agent` 的 `/api/events?after=N` 先用 `store.events_after(N)` 从 SQLite 回放，再接入实时广播（ADR 0018）。因此用旧游标重连不丢事实，不需要任何补偿步骤。

## 决策

- **`Resync` 结束当前订阅，不写节点状态。** 节点视图保持原样，不广播 `node_status_changed`。
- **不重置游标。** 重连继续用 `last_id`，从最后消费的事实续传，由 `agent` 的 SQLite 回放补齐。
- **退避回到最短等待。** `resync` 不是失败，重连序号归一到第一次重连的节奏；持续落后时按底数周期重连，而不是指数翻倍。
- **日志用 `debug`。** 持续落后会反复出现同一条记录，`info` 会淹没日志。
- **上游 `resync` 不外传。** 客户端看到的 `resync` 只由 `hub` 自己的回放窗口产生（ADR 0021）。两件事原因不同，不能共用一条指示。

## 备选

- **保留「失败」语义**（现状）：状态机简单，但把健康节点标成不可达，直接违反 ADR 0021 的状态机定义。
- **把 `resync` 当成流正常结束**：调用方无法区分「上游关闭流」与「要求重连」，于是要么两条路径都写状态，要么都静默，日志里也看不出区别。
- **重连时重读水位**：会永久跳过 `last_id` 与水位之间的事实，是丢事实的写法。

## 后果

- 节点状态只在真实不可达或版本不匹配时改变，`unreachable` 的说明重新可信。
- 「上游落后」变成一条只在日志里可见的正常事件；判断节点是否活着看状态，看落后看日志。
- 上游持续落后时表现为按底数周期重连。要根治必须加大 `agent` 的广播容量，那属于节点运维议题，不在本决策内。
