# ADR 0029: 合并 bootstrap 的广播水位在任何节点请求之前取

- 状态：已取代。见 ADR 0048（合并 bootstrap 随 hub 删除）
- 日期：2026-11-20

## 背景

合并 bootstrap 逐节点取快照，再返回 `max_hub_seq` 作为客户端游标的起点。实现把 `max_seq()` 放在循环末尾，于是快照期间发布的事实既不在快照里，也不在游标之后：客户端永远收不到它。首屏与每次 resync 都会碰到这条路径。

直觉上的写法恰恰是这个 bug：「快照做完了，再取最新的序号当作游标」。ADR 0018 已经定义了正确方向：水位取自快照读取之前，快照包含水位及之前的全部事实，水位之后的由回放补齐。

## 决策

- **水位前置**。`bootstrap` 在发起任何节点请求之前取一次 `bus.max_seq()` 并作为 `max_hub_seq` 返回。
- **重叠由客户端去重**。快照期间发布的事实同时出现在快照与回放里；客户端按 `(node, 事实 id)` 去重，广播序号按单调去重。两条路径都幂等，因此不必在 `hub` 侧裁剪。
- **探测并发**。各节点的 `/api/bootstrap` 并发发起，响应仍按节点表顺序排列。窗口期因此是「最慢的节点」而不是「节点之和」，首屏延迟也不再随节点数线性增长。

## 备选

- **快照完成后再取游标**（现状）：便宜，丢事实。
- **每节点各取一个游标**：客户端要 N 个游标，ADR 0021 已否决向量游标。
- **溢出兜底**：游标与当前序号的距离超过回放窗口时，bootstrap 直接回 resync 指示。客户端再取一次 bootstrap 会得到同样的结果，除非另加限流，否则这是新造的活锁风险。窗口期已由并发探测压到时延一侧，不引入。

## 后果

- 客户端游标可能比快照的实际水位更旧，代价是多回放几条事实，由去重消化。
- 若快照期间产生的事实超过回放窗口（4096 条），客户端立即收到 resync 并再取一次 bootstrap。此时表现为启动稍慢，不丢事实。
- `max_hub_seq` 从此是**下界**而不是「快照的最新位置」，任何「等于当前最大序号」的假设都不成立。
