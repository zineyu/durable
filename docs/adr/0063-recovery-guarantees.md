# ADR 0063: 崩溃恢复的保证来自令牌、证据强度与进程独占

- 状态：已接受。补充 ADR 0037 的工具结局四态、ADR 0047 的已中断消息、ADR 0056 的崩溃点矩阵、ADR 0059 的类别表边界、ADR 0060 的证据落点与 ADR 0062 的矩阵契约；同时登记本轮不做的范围
- 日期：2026-11-05

## 背景

本轮（#78 至 #83）把「任意位置崩溃都能自动恢复」从一句话变成四条机制：工具结局四态、副作用许可证、证据落点表、崩溃点矩阵。`AGENTS.md` 的目标节按四条写出判断标准，但「为什么长这样」散在七篇 ADR 里，三处取舍没有一处成文：

- 顺序为什么由能力令牌守，而不是由一条 lint 规则或评审清单守；
- 证据为什么必须分两档，而不是只有「发生过」；
- 并发为什么是单进程独占，而不是按实例租约；以及 duroxide 在同类问题上四处选择相反的理由。

缺一篇总账的代价是具体的：下一个改 `engine/tools.rs` 的人看不到「先提交再生效」为什么长成令牌的形状，会把它简化成一次函数调用；下一个提议加持久化定时器或多 worker 的人会重走一遍已经被否决的路。

## 决策

### 一、顺序由类型守，不由 lint 守

lint 看得见调用，看不见提交。要它守「副作用发生在一次提交之后」，它必须回答「这次执行之前，那一行走的是哪条事务、提交成功了没有」。三件事让这条检查不成立：写入在 `Store` 的写入线内完成（ADR 0012、ADR 0056）；证据的落点判定在另一个 crate（ADR 0060）；而 ADR 0032 已经禁止生产代码里出现抑制，把顺序写成可抑制的告警，等于自己开一个例外。

能力令牌把顺序做成接口的形状：

- `declare` 与 `dispatch` 都先调用 `Ledger::write`，写入失败时不发出许可证；
- 许可证的字段私有，也没有构造入口，因此外部无法凭空造出一张（`crates/effects/src/token.rs` 的两个 `compile_fail` 用例钉住这一点）；
- 执行接口只收已下发的许可证：`ToolBox::execute` 的第三个参数是 `Dispatched<EffectIntent>`。因此「没提交就发帧」编译不过。

三条硬保证的落点：

| 保证 | 落点 |
| --- | --- |
| 没有登记就执行不了 | `ToolBox::execute` 只收 `Dispatched`，它只能由 `dispatch` 产出 |
| 执行完不写结局不行 | `perform` 先写库再返回结论；`Outcome` 与 `Dispatched` 都是 `#[must_use]` |
| 令牌不串行化并发 | 许可证只含意图与密封标记，不持锁、不带生命周期 |

lint 仍在守一条别的：`scripts/check-write-path.sh` 断言写入只发生在 `crates/*/src/storage/`。那条规则问的是「写有几个入口」，不是「执行之前是否已经写过」。

### 二、证据分两档，重启按证据分流

`Evidence` 两个值：`Declared`（已登记、未下发，动作一定没有发生）与 `Dispatched`（已下发，动作可能已经发生）。分档的理由是一条事实：进程死在提交之后与副作用之前，与死在副作用之中，是两件不同的事；重启时能拿到的只有提交前缀，因此只有证据强度能把这两件事分开。

`settle` 把证据、类别的重放策略与幂等标记合成一个答案，规则逐条写死：

1. `Declared` → `Redo`，不看类别；
2. `Dispatched` 且策略为 `IfIdempotent` → 幂等取 `Redo`，否则 `GiveUp`；
3. 其余原样返回类别的策略。

不分档只剩两种收尾，两种都错：全部重发会重复非幂等副作用；全部放弃会丢掉可以安全重做的动作。分档之后，非幂等工具在崩溃后写「结果未知」，run 继续，模型看得到这次调用没有观测到结局。这就是「至多一次 + 未知可见」的来源。

### 三、单进程独占，不设实例租约

本系统是一台机器上的单用户 agent：一个 `agent` 进程、一份 SQLite、一个浏览器入口。租约是为「同一个实例被多个 worker 争抢」准备的：它需要租期、续期、fencing token、过期接手与幂等重放，每一样都要进状态，恢复路径因此要读租期与拥有者，而不只读领域行。

独占把这件事降到零：一个数据目录只允许一个进程，第二个进程打不开就退出。恢复因此只读库，不问「我是否仍然拥有这个实例」。

独占尚未落地（#41；#76 是它的实现条目）。锁落在数据目录里与数据库同级的锁文件上，而不是数据库本体：失败的一方要读出占用者的 pid，而被独占锁住的数据库文件读不出来。落地之前，「单进程」是约定，不是强制。

### 四、副作用库不持有存储，也不算运行时

`effects` 只回答四件事：类别表（名字、重放策略、覆盖声明）、许可证与四条流程、覆盖率、崩溃点契约。它不做 I/O、不定义错误类型、不规定账本落在哪里、也不计时（ADR 0059）。代价是使用方要自己写 `Ledger`；换来的是第二个使用方（一个 job 系统、另一个 agent）不必改库。

## 与 duroxide 的四处刻意差异

duroxide 是 Microsoft 的 Rust 持久化执行运行时（<https://github.com/microsoft/duroxide>）：内嵌 Tokio，用 `Provider` trait 抽象存储，SQLite provider 内建。它解决同一类问题，四处与本系统相反。四处都是刻意的。

| 轴 | duroxide | 本系统 | 理由 |
| --- | --- | --- | --- |
| 恢复方式 | 重启重放 history，逐圈重建内存状态；因此编排必须确定（用 `ctx.utcnow`、`ctx.select2` 替代时钟与 `tokio::select!`），运行时有不确定性检测 | 恢复点是状态的函数：`engine/plan.rs` 只读消息树决定下一步，不读时钟、不读环境、不重放历史 | 编排就是一个模型驱动的循环，没有「同一段代码再跑一遍」的语义。重放要求一套闭合的确定性 API（时钟、随机、并发、定时器都得从上下文取），那是另一个产品的形状 |
| 已下发未观测 | peek-lock：`lock_timeout` 到期后另一个 worker 取走重跑，投递是 at-least-once，因此活动必须可重入 | 证据分档，按类别策略与幂等分流；非幂等工具写「结果未知」，不重跑 | at-least-once 把「可重入」变成每个活动的义务。本系统的工具写文件、跑命令，多数不满足；承诺至多一次，未知就写未知 |
| 并发归属 | 实例锁与会话锁：`fetch_orchestration_item` 带锁，`renew_*_lock` 续期，`abandon_*` 释放 | 单进程独占数据目录：没有实例锁、没有续期、没有 fencing token | 见决策三 |
| 库的边界 | 运行时：`Provider`、队列、会话、持久化定时器、continue-as-new、durable KV、重试预算 | 库：类别表、许可证、覆盖率、崩溃点契约；存储、错误、日志、超时归使用方 | 见决策四。只有一个使用方时，把运行时抽象出来只是多一层 |

这张表的用法是反过来的：有人提议加重放、加投递重试或加多 worker 时，先读它。

## 备选

- **用 lint 或评审清单守顺序**：能提醒，不能证明。代价见决策一；它还会与 ADR 0032 冲突。
- **单档证据（只有「发生过」）**：状态更简单。代价是恢复只能二选一：重跑或放弃。
- **按实例租约**：同一份库可以由多个 agent 打开。代价是租期、续期与 fencing 进入状态，恢复路径要区分「我的租约还有效」与「别人接手了」；本机没有第二个 worker 来兑现代价。
- **照 duroxide 做历史重放**：恢复的语义更接近教科书。代价是编排代码必须放弃时钟与随机，模型驱动的循环无法满足；本系统也不需要「重放一段已经跑完的代码」。
- **让 `effects` 自带 SQLite 账本**：使用方少写一个 `Ledger`。代价是库持有表结构与迁移节奏，第二个使用方的存储被钉死。
- **把矩阵断言写成 `assert!`**：更短。由 ADR 0062 否决：第一条断言失败后其余点与坐标都不再被检查。

## 后果

- `AGENTS.md` 的目标节指向本篇：决策一对应「副作用之前先落库」，决策二对应「崩溃点就是提交前缀」推出的重跑与「结果未知」，决策三对应「边界写明」的进程边界，决策四对应「恢复点是状态的函数」。
- 顺序的保证不降级成告警（ADR 0032）：新增副作用时，接口收令牌，不收一个「记得先写」的注释。
- 单进程独占尚未落地。它落地时更新决策三，并把 #41 从台账上划掉。
- 恢复时间的保证由各介质层的截止时间给出，不由本库给出（ADR 0059）。
