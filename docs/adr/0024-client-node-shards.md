# ADR 0024: 客户端分片状态与广播游标

- 状态：已接受
- 日期：2026-11-04

## 背景

ADR 0021 把 `hub` 变成总线：客户端只面对一条合并事件流，游标是 `hub_seq`。每个 `node` 仍有自己的 SQLite 与事实事件 id，快照（合并 bootstrap、`SessionTree`）带的是 node 级水位。

ADR 0018 的续传只有一个游标，且事实事件 id 就是快照水位。多节点下这条路走不通：`hub_seq` 与 node 事件 id 是两个序号空间，`hub` 没有二者的映射。`SessionTree` 快照可能比已应用的尾部旧，客户端无法用 `hub` 游标重放这段尾部。

## 决策

**状态分两层。** `ClientState` 是 `{ hub: { nodes, cursor }, nodes: Record<node, NodeState> }`。`hub` 层持有节点表与广播游标（选中位置的处置见下文与 ADR 0044）；`NodeState` 分片持有该节点的 model、workspace、session、树与已应用的最大事实事件 id。分片由既有事实归约推导，分片之间互不影响。

**分片只在快照落地后存在。** 非 `ok` 节点没有分片，其列表为空。分片建立前到达的事实只推进广播游标，不建立分片；`ok` 状态到达时客户端取一次节点作用域的 `bootstrap`。事实包含在快照里，因此丢弃早到的事实不丢数据。

**广播游标与分片水位分开。** 带 `hub_seq` 的事件推进 `hub.cursor`。已应用过的 `hub_seq` 直接丢弃。分片水位只由事实 id 决定，用于分片内的幂等去重。

**快照在分片内补齐尾部。** 应用快照时，分片水位取 `min(水位, 快照水位)`，分片保留最近若干条已应用事实；随后按升序重放缓存的、id 大于快照水位的事实。`hub.cursor` 不回退：回退它只会重放已丢弃的广播序号。

**选中节点是 URL 的一部分。** `#/n/<node>/s/<session_id>` 决定选中节点与 session，URL 哈希是选中位置的唯一所有者。切换节点因此零网络请求，分片内容不变。ADR 0044 删除了 `hub.selected`：它只写不读，与哈希并存会让同一份状态有两个所有者。

## 后果

- ADR 0018 的「快照落地时回退游标并重开事件流」在客户端只保留在广播游标上；节点级快照靠分片内重放补齐，不再重建连接。
- 分片的重放缓存有界。快照落后超过缓存深度时，这段尾部丢失；该差距远大于一次快照往返，实际只在极端情况下出现。
- 事实事件跨节点没有全局顺序，客户端不得依赖跨节点因果；顺序只在分片内成立。
- reducer 测试按分片调用：重复事件只影响对应分片，两节点事件交错时互不影响，切换节点不改变分片。
