# ADR 0047: 流式进度落库与已中断消息

- 状态：已接受。取代 ADR 0037 的「assistant 消息只在流正常结束时入树」一条决策
- 日期：2026-10-27

## 背景

ADR 0037 让恢复点完全从树推导，代价是 assistant 消息只在流正常结束时入树。进程被杀或机器断电时，正在流式输出的整段回答丢失，用户看到「run 失败，没有内容」。一次长回答可能已经运行了十分钟。

用户取消走的是同一条路径：已经生成的内容同样丢弃。

## 决策

**流式正文按时间节流写入 run 的进度**。`run` 表新增 `progress` 列，保存当前这一步已经产生的正文。间隔由 `DURABLE_PROGRESS_INTERVAL_MS` 配置，默认 100 毫秒；内容没有变化时不提交。进度只存文本：推理与未完成的工具调用都不写入，因为它们对续跑没有意义。

**进度写入不登记事实事件**。它不修改 session 视图，不推进 session 的 `updated_at`，不广播任何东西。客户端本来就有实时增量，落库只为崩溃恢复。`Changeset` 因此新增一个写进度的变更种类，该种类不参与 `SessionCommand::view()` 的推导。

**已中断是消息级标记，不是块状态，也不是 run 失败类别**。`MessageSkeleton` 与消息行新增 `interrupted`。它描述「这条消息是部分输出」，而不是「某个块还没完成」。run 失败类别 `interrupted` 保持只为读出历史值。

**转换点只有一个**：把进度入树为一条标注已中断的 assistant 消息，并在同一事务里清空进度。消息 id 由全局分配器新铸，父节点是该 run 的 active leaf。启动恢复与用户取消共用它。因为入树与清空在同一事务，不存在「消息已入树、进度仍残留」的状态，恢复途中再次被杀也不会写出第二条消息。

**定型与清空进度也在同一事务**。这一步正常结束时，`append_assistant` 同时写消息与清空进度。run 结束时 `finish_run` 同样清空，因此结束的 run 没有进度。上游失败不产生已中断消息：部分输出随 run 结束一起丢弃，沿用 ADR 0037 的语义。

**续跑推导遇到已中断消息时发请求**。ADR 0037 的规则是「末条 assistant 没有工具调用时收尾」，部分输出正好落在这个形状上，因此必须新增一条分支：树尾是已中断的 assistant 消息时发一次模型请求。

**装配请求时合并相邻 assistant 文本**。中断前的部分输出与续跑产出在同一条回答里，装配上下文时把相邻 assistant 节点的文本直接拼接成一条 wire 消息，不插入模型没有写过的分隔符。

**消息骨架新增字段是兼容改动**。该字段带 serde 默认值：迁移 0010 之前的事件行没有它，旧 hub 转发的载荷也没有它。旧 hub 忽略新字段，新 hub 读旧载荷得到 `false`。协议版本因此不递增。

## 后果

- 崩溃最多丢失一个节流窗口的内容，而不是整段回答。用户看到的部分回答带「已中断」徽标，不会误当成完整结论。
- 磁盘写放大受节流间隔约束：默认每 100 毫秒最多一次单行更新。
- 模型看到的上下文里，一次中断的回答仍是一条 assistant 消息，续写不会出现「模型自己没写过的过渡句」。
- 客户端多一个消息状态 `interrupted`，它优先于 run 状态：后续 run 的结局不改这条消息的标记。
- 非幂等工具被切断时的「结果未知」与本次改动无关，仍由 ADR 0037 的恢复逻辑负责。
- `RunRecord` 变大使 `FactEvent` 超过 clippy 的 `large_enum_variant` 阈值，因此 `RunStarted` 与 `RunFinished` 的 `run` 改为装箱。JSON 载荷与生成的 TS 类型不变，只有 Rust 侧构造与匹配要加一层。

## 备选

- **按增量字节数节流**：写放大随内容长度波动，调参不直观。按时间更接近用户感知的「最多丢失多少」。
- **为进度建立独立表**：进度是 run 的单一属性，同一时刻最多一行。独立表只增加一次连接与一次清理。
- **把已中断做成内容块状态**：块状态描述的是工具结果，用它表达「整条消息不完整」会让装配与渲染都多一层推断。
- **恢复时把进度接进下一条 assistant 消息**：消息一旦入树就不可变，续跑写入新消息更简单，也让「每条消息只写一次」保持成立。
