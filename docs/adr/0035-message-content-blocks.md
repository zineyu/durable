# ADR 0035: 消息历史存完整内容，节点正文为内容块数组

- 状态：已接受
- 日期：2026-10-22

## 背景

原实现把节点正文压成 `message.text` 加 `message.tool_calls`：推理内容被丢弃，工具结果只以 `ToolOutcome` 内嵌在工具调用记录里，图片无从表达。provider 直接在引擎里按上游格式拼装请求，因此「历史里有什么」与「实际发了什么」两条线各自演化。

新要求：所有可能发给模型的内容都在树中存储，含推理、工具调用、工具结果、用户消息与 assistant 消息；预留多模态输入；不存 `system` 角色（系统提示由请求装配层提供）。压缩结果另篇（ADR 0036）。

## 决策

**节点是一条消息，正文是有序的内容块数组**。`role` 取 `user`、`assistant`、`tool`、`compaction`；内容块是类型化枚举，首期有文本、推理、工具调用、工具结果，图像与其它多模态块随后加入而不改表结构。节点不再有 `text` 字段。

**assistant 节点承载一次模型回复的全部内容**：推理、文本与它请求的工具调用都是这条消息的块，顺序即产生顺序。一次回复是不可分的协议单位：上游要求工具调用与其结果严格配对，部分供应商要求推理与其所属的 assistant 消息一起回传。

**工具结果是独立节点**。每条工具结果是对应 assistant 节点的子节点，`role` 为 `tool`，块里带工具调用 id 与结构化结局。父子链因此严格线性：assistant → tool → tool → 下一个 assistant。理由：assistant 消息在流结束时定型，工具结果在各自执行完毕时产生并自带时间戳与失败码；独立节点让「已定型」与「仍在追加」不共用一行；取消发生在第 2 个工具时，第 1 个工具的结果作为完整事实已经落库。

**落库为两表**：`message`（id、session_id、parent_id、role、run_id、created_at）与 `message_part`（message_id、seq、kind、body）。块一行一块，`body` 是该块主体的 JSON。

**块级写入**。一块一行，写入与更新都以块为单位：定型消息的块一次写齐，工具节点的结局是一次块更新。流式中的部分输出不落库（ADR 0037）；大块（工具结果）一行写一次，此后不再重写。`kind` 与 Rust 的块枚举是同一形状的两面，数据库只保证 `seq` 顺序与 `kind` 合法性。

**provider 是唯一的格式转换点**：内核只产出内容块，provider 把内容块序列翻译成上游可接受的形状。转换规则不属于本节。

## 后果

- 树是完整历史：推理、工具结果与图片都在树里，快照与事件流都能重建客户端视图。
- 一次 run 产生的不再是单个 assistant 节点：一次回复一个 assistant 节点，每条工具结果一个 tool 节点。事件流按节点追加与更新走，部分输出只走实时增量。
- 协议类型改动不小：`MessageNode` 的 `text`、`tool_calls` 换成块数组，TS 类型与客户端渲染同批改。
- 存量数据库需要重建 `message` 表并回填：旧 `text` 成为文本块，旧工具调用成为工具调用块与对应 tool 节点。
- 存储体积显著上升（工具输出原样入树）。因此快照与事件只带骨架，正文按需拉取（ADR 0038）。
- `message_part` 的 `body` 不可直接 SQL 查询；未来搜索功能需要从块派生的索引列，而不是现在预埋。
