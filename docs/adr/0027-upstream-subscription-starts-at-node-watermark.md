# ADR 0027: 上游订阅起点取节点快照水位

- 状态：已取代。见 ADR 0048（上游订阅随总线删除）
- 日期：2026-11-20

## 背景

ADR 0021 决定了 `hub` 是总线，且不持久化广播状态。它没有回答一个下游问题：每个 node 的上游订阅从哪个事实 id 开始。实现选了 `0`，于是 `hub` 每次重启、节点每次改名、每次删除后重注册，都会让该 node 的全部历史事实重新进入合并流：`agent` 全量回放，4096 的回放窗口被冲爆，所有客户端重复应用几千条事实。

两条路线：持久化每个 node 的上游游标，让它跨 `hub` 进程延续；或者每次建立订阅时从节点当前水位开始。

## 决策

**上游订阅起点是该 node 的快照水位**，即首次连接时读 `BootstrapResponse.max_event_id` 并用作 `/api/events?after=N` 的 `after`。

- `hub` 不持久化这个游标，也不用它做任何恢复：每次（重）连重新取。
- `hub` 重启后的缺口不由事件补发修复，而由客户端 resync 后重新获取的合并 bootstrap 快照修复（ADR 0018、ADR 0021）。
- 读 `max_event_id` 失败按原有失败路径重试，不影响状态机：状态仍由后续 `run_stream` 的结果决定。

## 备选

- **持久化上游游标**：只有停机时间短于回放窗口时才省掉 resync；长期停机照样回到 resync，于是两套恢复机制并存，还要一条写入线维护游标与窗口的一致性。ADR 0021 已把这条列为「`hub` 级 id 持久化」并否决。
- **省略 `after` 即实时尾部**：把「从此刻开始」编码进 `agent` 的 `/api/events` 语义。省一次请求，但把「传 `after=0` 全量回放」变成 URL 上唯一可见的能力，且 `agent` 与 `hub` 必须同时升级。
- **在 `/api/health` 加 `maxEventId`**：请求最轻，但要破「不新增协议字段」约束并递增协议版本。`bootstrap` 已经有这个字段，重用它不需要动协议。

## 后果

- 每次上游（重）连多一次 `bootstrap` 请求；响应里的 workspace 与 session 列表被丢弃。
- 同一原因持续期间不再产生重复的事件，回放窗口只花在真实变化上。
- 「事件流没有丢事实」这句话只在单个 `hub` 进程的生命周期内成立；跨进程的完整性由快照承担。
