# ADR 0056: 崩溃点是提交前缀，矩阵逐个重启

- 状态：已接受。细化 ADR 0037 的「恢复点从树推导」与「测试必须能杀掉进程」，落实 ADR 0046 的 seam 五、seam 六
- 日期：2026-11-03

## 背景

ADR 0037 的后果里写着：「恢复逻辑的测试必须能杀掉进程：测试要能构造出『库里恰好停在某个检查点』的状态并断言续跑结果。」实际只有两个进程级检查点被断言（流式中、工具执行中）。其余检查点靠人读代码判断「应该能续跑」，于是「在任意位置崩溃都能自动恢复」是推理，不是证据。

两个观察让这件事变成可程序化的：

1. **事务是原子的**。SQLite 单文件 + WAL + `synchronous = Full` 意味着一次崩溃只可能落在「某个提交已完成、下一个尚未开始」之间，或落在一个未提交的事务里——后者回滚后等价于前一个提交点。**全部提交前缀就是全部崩溃点**，不需要真的杀进程来抽样。
2. **恢复判定是纯函数**。`engine/plan.rs::next_action(transcript, run, max_steps)` 只看树，不读时钟、不读环境。所以「任意前缀都能推出下一步」可以被穷举。

前提是第三条：**全部持久化写都经过 `Store::commit`**。绕过它一次，前缀集合就不再等于崩溃点集合。

## 决策

**提交点副本**。`Store::open_recording(path, directory)` 在每次提交成功后写一份 `prefix-<n>.sqlite`（`VACUUM INTO`，一个读事务里写出一致的副本）。生产路径用 `Store::open`，`Option<PathBuf>` 为 `None`，不产生任何副本，也不多一次 IO。`Store::commits()` 暴露已提交次数，夹具用它把副作用对齐到提交点。

**矩阵逐个重启**。`apps/agent/tests/crash_matrix.rs` 跑一个场景（Seam 六：真 `Store` + 替身执行端），拿到全部副本，然后对每个副本：打开、`RunEngine::recover()`、跑到静止，断言五条性质——恢复收敛；`check_invariants()` 为空；崩溃前的链仍是重启后链的前缀；没有停在执行中的工具节点；非幂等调用跨「崩溃前 + 重启后」至多执行一次，幂等调用至多两次，且重跑过的调用必须留下结局。另有一条用例钉住未下发与已下发的分界：已入树但帧未下发的非幂等调用一定没有执行，恢复把它重跑一次而不是写成「结果未知」，缺陷 #67 随之关闭。

**不变量成为领域检查**。`Store::check_invariants()` 返回违例清单，九类：同 session 多条 running run、`progress` 留在已结束的 run 上、没有 running run 却有执行中的工具节点、同一调用多个结局节点、结局找不到调用、active leaf 不在树上、队列锚点不在树上、id 分配器落后、已结束 run 里声明的调用缺结局。`RunEngine::round_zero` 在**修复之后、run 真正开始之前**检查一次并只记日志；矩阵把它当硬断言。

**单一写入线由脚本守门**。`scripts/check-write-path.sh` 断言：`.apply(changes` 只出现一次、`apply_change(&mut transaction` 只出现一次、`sqlx::query` 与写 SQL 不出现在 `crates/*/src/storage/` 之外。它在 `durable-lint` 的 `scripts/check-*.sh` 循环里跑。

**恢复判定的有界性用随机树尾穷举**。`plan.rs` 的单元测试生成随机的树尾形状（空树、用户消息、压缩消息、已中断的 assistant、带调用的 assistant、批次中间的工具），按与 `drive_run` 相同的规则把动作作用回树上，断言 64 步之内收尾。空的工具批次直接判失败——那正是活锁的形状。

## 后果

- 「任意位置崩溃」从一个主张变成一组可断言的有限集合：每个场景 10 至 25 个提交点，全套毫秒级，随 `cargo test --workspace` 跑。
- 新提交点自动纳入：只要它经过 `Store::commit` 就会留下副本，矩阵无需为它加用例。反过来，想绕开矩阵就得绕开写入线，而那条路被脚本拦着。
- 矩阵会随代码增长：提交点越多，副本越多。目前三个场景共 50 个副本、0.8 秒。
- 副作用日志与提交点对齐是夹具的责任：替身执行端在效果发生时记下 `commits()`，断言据此区分「崩溃前已发生」与「重启后重跑」。
- `Store` 多了一个字段与一处调用，属于生产代码里为测试存在的支持。它的理由是这个 seam 换来的是一份穷举证据；开销为 `None` 时的一次判空。
- 三条边界没有因此被覆盖：外部副作用的恰好一次（`bash` 的任意命令没有 2PC）、进程悬挂（活在但不回应，需要 #65 的上界才谈得上收敛）、介质损坏（`synchronous = Full` 覆盖断电，不覆盖坏盘）。

## 备选

- **随机杀进程（混沌）**：抽样而非穷举，还要靠等待与超时，慢且不稳定。保留给 e2e 与 nightly，作为「故障模型之外」的信号，不进 `durable-test`。
- **在 `SqliteStorage` 上加 `CommitObserver` trait**：收益与 `open_recording` 相同，多一层间接与一次虚调用；副本是唯一用途，不值得通用化。
- **用 sqlx 的备份 API**：sqlx 没有暴露；`VACUUM INTO` 一行就够，且是 SQLite 官方的一致副本语义。
- **模型检验（TLA+ / Stateright）**：能给出协议级证明，但模型会与代码漂移，维护成本高于收益。先用「随机树尾 + 有界步数」这条纯函数穷举顶上；语义真有争议时再升级。
- **把 `check_invariants` 接进 `/api/health`**：会把只读健康检查变成一次全库扫描，暂不做。

## 待定

- 副本数量随场景增长，是否需要按场景只保留「形状不同」的副本（去重）。
- 矩阵要不要覆盖取消与插话场景：两者都需要一个确定性的注入点，而目前没有。
- 缺陷 #67 落地之后，`crash_matrix` 里固定现状的那条用例要改成「未下发的调用被重跑」。
