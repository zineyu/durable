# ADR 0037: 崩溃恢复的续跑点从树推导

- 状态：已接受。两条结论由 ADR 0047 取代
- 日期：2026-10-22
- 状态说明：取代 ADR 0014 的「节流落库部分输出」
- 状态说明（2026-10-27）：本篇的「assistant 消息只在流正常结束时入树」与后果里的「「部分输出」不再是持久事实」由 ADR 0047 取代，其余决策仍然有效。
- 状态说明（2026-11-04）：工具节点的未观测态拆为已登记未下发与已下发未观测，见文末「工具结局四态」。其余决策仍然有效。
- 状态说明（2026-11-04）：恢复判定并入每次开跑前的第 0 圈，启动路径不再有专用收尾函数；恢复按证据强度分流，见文末「恢复按证据强度分流」。

## 背景

durable 的语义要求进程在任意时刻被杀之后，重启能自动继续，不需要人工干预。原实现每 100 ms 把部分输出写回 assistant 节点，重启后无法区分「一条正在生成的消息」与「一条已经结束、正等工具执行的消息」，也分不清「工具还没开始」与「工具执行到一半」。

## 决策

**恢复点不额外存状态，从树推导**。启动时对状态仍是 `running` 的 run，看它 `active_leaf` 方向的最后一条消息：

- 末条是 user 消息：发请求生成本步。
- 末条是 assistant 消息且仍有工具调用没有对应 tool 节点：执行这些工具。
- 末条是 tool 节点：找到最近的 assistant 消息，若它仍有无对应 tool 节点的调用，先补齐这些调用；否则发下一次请求。
- 末条是 assistant 消息且没有工具调用：run 正常收尾，状态改为 `succeeded`。

**assistant 消息只在流正常结束时入树**。流中途的内容不落库，只在内存与实时增量里传输。因此在流中途崩溃不会留下任何痕迹，该步直接重跑。用户看到的代价是刷新页面丢掉正在生成的内容，收下的收益是「半成品」这个概念不存在。

**tool 节点在开始执行前入树**，状态为已登记未下发；交给执行端之前改写成已下发未观测；执行完毕写入结局。因此「这一批工具有几个已跑完」可以直接从链上读出：assistant 的调用列表减去已有 tool 节点的调用就是待办的。恢复时遇到结局未观测的工具：

- 工具幂等：重跑并覆盖结局。
- 工具非幂等：结局写为「结果未知」——它不是工具返回的错误，而是我们丢失了对结果的观测。

**工具定义带幂等标记**。`read_file` 与 `write_file` 幂等；`edit_file`（第二次会找不到原文）与 `bash`（外部副作用）不幂等。

**崩溃不产生新的 run，也不移动队列**：resume 用的还是那条 `running` 的 run，队列项在 run 开始时就已出队。

## 后果

- 每一步都「先落库再执行」：发起模型请求前、执行工具前、写工具结局前，可恢复状态都已提交。崩溃只会让某一步重做，不会让已提交的副作用消失。
- 非幂等工具的最坏情况是重复执行被写进历史的风险被消除，代价是那一刻的结果只能记为未知，由模型判断下一步。
- 「部分输出」不再是持久事实：它只经实时事件传输，客户端刷新会丢失。原 ADR 0014 的节流落库被移除。
- 客户端需要区分「进行中的步」与「已入树的消息」：进行中的内容挂在即将定型的消息 id 上，定型后由 `message_appended` 接管（见 ADR 0038）。
- 恢复逻辑的测试必须能杀掉进程：测试要能构造出「库里恰好停在某个检查点」的状态并断言续跑结果。

## 状态说明（2026-11-04）：工具结局四态

**结局分四个取值**：`declared`（已登记未下发）、`dispatched`（已下发未观测）、`finished`（有结局）、`unknown`（结局未知）。两个未观测态的顺序即写入顺序：节点先以 `declared` 入树，下发前写一次 `dispatched`，再把结局或 `unknown` 写回同一节点。`dispatched` 因此表示「执行端可能已经有副作用」，`declared` 表示「一定没有」。

**旧库的 `running` 读作 `dispatched`**。用 serde 的 variant 别名接住，写出只产生 `dispatched`，不需要数据迁移。读入规则的测试在 `crates/core/src/tool.rs`。

**骨架只有三种状态**。`PartState` 仍是 `complete`、`running`、`unknown`，两个未观测态都归入 `running`。存储的 `message_part.state` 因此仍只有三种取值：读取未观测工具节点的查询写 `state = 'running'` 即同时覆盖两态。骨架不区分两态的理由是呈现层不区分：界面上两者都显示为执行中，用户可见行为不变。

**模型看到的工具结果文案不变**。两个未观测态回传模型时同为 `{"error":"running","message":"工具仍在执行"}`，因此形态扩张不改模型输入。

**`ts-rs` 不建模 serde 的 variant 别名**，遇到 `alias` 会打印一条伪告警。工作区因此启用它的 `no-serde-warnings` 特性：serde 自身仍校验属性名，被忽略的只是 ts-rs 无法投影的部分。

## 状态说明（2026-11-04）：恢复按证据强度分流

中断现场在每次开跑前的第 0 圈处置，启动恢复与日常续跑走同一条路：先把流式进度入树为已中断消息，再逐个看结局未观测的工具节点。判定由 `effects::policy::settle` 给出，输入是证据强度、类别策略与工具定义上的幂等标记：

- 已登记未下发：计划重跑。工具一定没有执行，非幂等也不例外。旧实现在启动时把它写成「结果未知」，因此 `bash` 与 `edit_file` 在最该重跑的窗口里被放弃（`#67`）。
- 已下发未观测且工具幂等：计划重跑，结局覆盖原节点。
- 已下发未观测且工具非幂等：写「结果未知」，不重跑。
- 结局未观测但找不到对应调用：写「结果未知」。计划无法重跑一条找不到调用的节点，留着它只会一直显示「执行中」。

三个提交点由许可证串起来（`effects::token`）：登记先落一行「已登记」，发货写着「已下发」并换出发货许可证，执行只接受这张许可证，收货把结局写回同一节点。取消与断链把在途调用写成「结果未知」，批次里剩下的调用经「登记 → 弃」同样写成「结果未知」，因此 run 结束时没有工具节点停在未观测态。
